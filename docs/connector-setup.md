# Connector setup and coverage

Mach 1 reads real customer conversation data using delegated OAuth. It does not send messages, modify source records, or accept pasted access tokens in the browser. An installed provider adapter is not evidence that its OAuth application has been approved or configured. `connectorReady` only reports whether its server client ID and secret exist; an account is connected only after a successful OAuth exchange and account identity readback.

## Initial providers

| Provider | Best fit | Access requested | Server variables |
| --- | --- | --- | --- |
| Gmail | Sales and support email | `https://www.googleapis.com/auth/gmail.readonly` | `CONNECTOR_GMAIL_CLIENT_ID`, `CONNECTOR_GMAIL_CLIENT_SECRET` |
| Microsoft 365 | Sales and support email | Delegated `User.Read Mail.Read offline_access` | `CONNECTOR_MICROSOFT_CLIENT_ID`, `CONNECTOR_MICROSOFT_CLIENT_SECRET` |
| HubSpot | Sales and support inbox conversations | `conversations.read` | `CONNECTOR_HUBSPOT_CLIENT_ID`, `CONNECTOR_HUBSPOT_CLIENT_SECRET` |
| Zendesk | Support tickets | `tickets:read users:read` | `CONNECTOR_ZENDESK_CLIENT_ID`, `CONNECTOR_ZENDESK_CLIENT_SECRET` |
| Intercom | Support and sales conversations, US region | Console permissions **Read conversations** and **Read one admin** | `CONNECTOR_INTERCOM_CLIENT_ID`, `CONNECTOR_INTERCOM_CLIENT_SECRET` |

Register this exact production redirect on each provider application: `https://flight-ai-two.vercel.app/api/product?action=connector.callback`. These connector applications are separate from Google/Apple sign-in applications. Set credentials only through the deployment secret store. Never commit credentials, paste them into product setup, or expose them to client JavaScript.

- Google: enable Gmail API, configure external consent/test users, and register a web OAuth client. Gmail read-only is a restricted scope; public launch may require Google's verification/security assessment. Request offline access and consent to obtain refresh access. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).
- Microsoft: register an Entra web app supporting the intended organizational and personal accounts; add the delegated permissions above, configure its redirect and a server client secret. Tenant policies may require administrator consent. Common-tenant authorization is used; no application-wide mailbox permissions. [Permissions](https://learn.microsoft.com/en-us/graph/permissions-reference), [authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).
- HubSpot: register a public OAuth application with Conversations read access. Only Inbox/Help Desk thread data is currently imported; CRM deal timelines, call recordings, and all historical CRM email engagements are not included. Token issuance and introspection use the current date-versioned endpoint with secrets in the POST body. [Threads](https://developers.hubspot.com/docs/api-reference/conversations-conversations-inbox-&-messages-v3/public-thread/get-conversations-v3-conversations-threads), [OAuth migration](https://developers.hubspot.com/changelog/v1-oauth-api-deprecation).
- Zendesk: register a confidential OAuth client with only the listed scopes. A local Zendesk client is tenant-specific; a public multi-customer launch needs Zendesk global OAuth client approval. Users provide only their subdomain (for example `acme`, not a URL). [OAuth setup](https://developer.zendesk.com/documentation/authentication/api-tokens-to-oauth/), [scopes and PKCE](https://developer.zendesk.com/documentation/authentication/oauth-migration/).
- Intercom: enable OAuth and select the two read permissions in Developer Hub. Permissions are selected in the provider console, not by arbitrary URL scope strings; do not enable write permissions. Public integrations require app review. Only US-hosted workspaces are supported initially; EU/AU need an explicit regional adapter before launch. Its documented access token flow does not issue refresh tokens; expired/revoked access requires reconnection. [OAuth and permissions](https://developers.intercom.com/docs/build-an-integration/learn-more/authentication/setting-up-oauth).

## What a scan covers

Scans are bounded batches, not a full account synchronization or a background monitor. The caller supplies 1–10 records per batch (production API uses its own lower bound), persists the returned cursor, and surfaces `hasMore`. Gmail enumerates threads. Microsoft enumerates recent messages then groups their conversation IDs; the same thread can appear again across pages and is deduplicated by the backend. HubSpot enumerates inbox threads. Zendesk reads accessible tickets. Intercom reads accessible conversations. Permissions and provider retention determine actual visibility.

- Gmail loads full MIME threads, preferring plain text and converting HTML when necessary. It does not download attachments. SENT labels and mailbox identity identify teammate messages; unrecognized senders are not employee identities. [Thread listing](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.threads.list).
- Microsoft loads up to 100 messages for each conversation and excludes drafts. Larger threads fail explicitly instead of being analyzed as complete. Only the authorized mailbox is read. [Message listing and paging](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0).
- HubSpot reads up to five message pages per thread, excludes comments and unsent/failed messages, and rejects provider-marked truncation. [Message history](https://developers.hubspot.com/docs/api-reference/conversations-conversations-inbox-&-messages-v3/public-message/get-conversations-v3-conversations-threads-threadId-messages).
- Zendesk reads up to five comment pages per ticket and excludes private notes. Sideloaded users identify roles; unknown participants retain an unknown role.
- Intercom includes the opening source and public comments; notes/system parts are excluded. It rejects responses at the 500-part cap because earlier parts may be missing. [Conversation retrieval limit](https://developers.intercom.com/docs/references/preview/rest-api/api.intercom.io/conversations/retrieveconversation).

Messages are bounded to 20,000 characters, threads to 500 messages, response bodies to 4 MB, and each provider operation to a 30-second request budget. Source errors/rate limits do not become an empty successful scan. Attachments, redacted content, and internal notes are not analyzed. This is conversation intelligence, not a completeness guarantee across all company communications.

Pagination tokens are encoded as data. Microsoft and Zendesk continuation URLs must exactly match the authorized HTTPS host and endpoint, and HTTP redirects are rejected. No user-controlled hostname is accepted. Token responses and provider error bodies never appear in user-facing errors. Account identity is read from the provider before recording a successful connection. The encrypted token record includes a stable `accountId` separately from the display label: Gmail mailbox email, Microsoft directory user ID, HubSpot portal ID, Zendesk tenant subdomain, or Intercom workspace ID. Reconnection must match this identity so two accounts with the same display name cannot overwrite each other's imported records. OAuth state, user/workspace binding, encryption, refresh-token storage, tenant isolation, scan locks, and cursor persistence are implemented in the backend.

## Verification before enabling each provider

Run `node --test tests/product-connectors.test.mjs`. Tests use documented representative payloads and mocked HTTP only. Then, with an approved test account, verify consent scopes, cancel/deny, callback state binding, source account label, refresh/reconnect, several continuation pages, and one known conversation. Confirm UI counts against imported records and confirm disconnect removes access. These manual provider checks require configured applications and have not been replaced by mock tests. Never call a connector “live” based on configuration alone.
